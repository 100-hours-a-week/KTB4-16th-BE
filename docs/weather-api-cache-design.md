# 날씨 API 및 일 단위 격자 캐시 설계

## 1. 문서 목적

이 문서는 MULO V1에서 기상청 단기예보 `getVilageFcst`를 호출하고, 한 번 받은 격자별 시간대 예보를 MySQL에 저장하여 같은 날 재사용하는 기준을 정의한다.

V1에서는 Redis를 도입하지 않는다. 날씨 캐시는 MySQL에 저장하며, 외부 API 호출 횟수 절감과 다수 사용자의 동일 격자 데이터 재사용을 최신 예보 반영보다 우선한다.

이 문서는 다음 기존 정책을 새로운 결정으로 대체한다.

- 요청 시각을 항상 현재 정각으로 내리던 규칙
- 새 발표 회차가 나올 때마다 같은 예보시각의 캐시를 갱신하던 규칙
- 최신 발표본 조회 실패 시에만 직전 발표본을 사용하던 규칙

## 2. 확정 범위

- 데이터 원천은 기상청 단기예보 `getVilageFcst`이다.
- 위도·경도를 기상청 격자 `(nx, ny)`로 변환한다.
- 한 번의 응답에 포함된 여러 `fcstDate + fcstTime`을 시간대별로 파싱한다.
- 파싱 결과는 MySQL의 격자별 예보 캐시에 일괄 저장한다.
- 같은 KST 날짜에 같은 격자의 캐시가 존재하면 외부 API를 다시 호출하지 않는다.
- 최초 저장한 발표 회차의 데이터는 당일 동안 유지하며 새로운 발표본으로 갱신하지 않는다.
- 저장·응답 대상은 기온과 MULO 내부 날씨 상태이다.
- 풍속, 습도, 강수확률과 원시 `PTY`·`SKY` 값은 V1 저장 및 응답 범위에서 제외한다.
- 과거 실황 API인 `getUltraSrtNcst`는 V1 범위에서 사용하지 않는다.

## 3. 시간 개념

기상청 응답의 시간은 다음처럼 구분한다.

| 이름 | 의미 | 예시 |
|---|---|---|
| 요청 시각 | 사용자가 MULO에 날씨를 요청한 KST 시각 | `2026-09-20 11:10` |
| `base_at` | 기상청이 예보를 생성한 발표 기준시각 | `2026-09-20 08:00` |
| `forecast_at` | 날씨가 적용되는 예보 대상시각 | `2026-09-20 11:00` |
| `fetched_at` | MULO가 기상청 응답을 받은 시각 | `2026-09-20 11:10` |

`baseTime`은 사용자가 요청한 시각이 아니다. 예를 들어 사용자가 11시 10분에 요청하더라도 기상청의 발표 회차는 `0800` 또는 `1100`이다.

## 4. 요청 시각과 예보시각 선택

요청 시각에서 시간 차이가 가장 작은 정각을 `target_forecast_at`으로 선택한다.

- 분이 `00~29`이면 현재 시간의 정각을 선택한다.
- 분이 `30~59`이면 다음 시간의 정각을 선택한다.
- 정확히 30분이면 다음 정각을 선택한다.
- 계산 기준 시간대는 `Asia/Seoul`이다.

```text
11:01 요청 -> 11:00 예보
11:10 요청 -> 11:00 예보
11:29 요청 -> 11:00 예보
11:30 요청 -> 12:00 예보
11:40 요청 -> 12:00 예보
11:59 요청 -> 12:00 예보
```

핵심 로직에는 다음 의도의 주석을 남긴다.

```java
// 중요: 단기예보는 정각 단위이므로 요청 시각과 가장 가까운 예보시각을 선택한다.
// 30분 미만은 현재 정각, 30분 이상은 다음 정각을 사용한다.
```

이 값은 실제 관측시각이 아니라 요청 시각과 가장 가까운 **예보시각**이다. 따라서 API 응답 필드도 `observedAt`이나 `currentWeatherAt`이 아니라 `forecastAt`을 사용한다.

### 4.1 요청 시간대와 과거 요청 검증

- `at`은 ISO-8601 offset datetime으로 받는다. `+09:00` 이외의 offset도 같은 실제 시각으로
  `Asia/Seoul`에 정규화해 판단한다.
- 전송 지연 때문에 프론트가 보낸 현재 시각이 서버 도착 시점보다 몇 초 앞설 수 있으므로,
  초 단위의 `at < 서버 현재 시각` 비교는 사용하지 않는다.
- 서버 KST의 현재 시간대가 시작되기보다 이른 `at`만 과거 요청으로 본다. 예를 들어 서버가
  `11:10 KST`이면 `11:00~11:59` 요청은 허용하고 `10:59` 이전 요청은 거부한다.
- 과거 요청은 좌표 변환, 캐시 조회, 기상청 호출 전에 `400 INVALID_WEATHER_REQUEST_TIME`으로
  처리한다.

## 5. 발표 회차 선택

발표 회차는 `target_forecast_at`을 포함하는 회차 중 사용 가능한 가장 최근 회차를 선택한다.

예를 들어 11시 10분 요청은 `forecast_at=11:00`을 필요로 한다. `baseTime=1100` 응답은 12시 예보부터 시작하므로 11시 예보를 얻기 위해 `baseTime=0800` 회차를 사용한다.

```text
11:10 요청
  target_forecast_at = 11:00
  baseTime=1100 응답에는 11:00이 없음
  baseTime=0800 응답의 fcstTime=1100 사용

11:40 요청
  target_forecast_at = 12:00
  baseTime=1100 응답의 fcstTime=1200 사용 가능
```

기상청 API는 HTTP 200이어도 아직 공개되지 않은 회차에 대해 `03 NO_DATA`를 반환할 수 있다. 후보 회차가 `NO_DATA`, 일시적 `APPLICATION_ERROR`, 네트워크 오류 또는 잘못된 응답 구조를 반환하면 직전 발표 회차를 제한적으로 시도한다.

직전 회차에서도 `target_forecast_at`을 확보하지 못하면 날씨 확보 실패로 처리한다. 무제한 재시도하거나 오래된 회차를 계속 탐색하지 않는다.

## 6. 캐시 정책

### 6.1 최초 요청

동일한 KST 날짜와 격자의 성공 캐시가 하나도 없을 때만 다음 순서로 처리한다.

1. 위도·경도를 기상청 격자로 변환한다.
2. 요청 시각을 가장 가까운 정각으로 변환한다.
3. 해당 예보시각을 포함할 수 있는 발표 회차를 결정한다.
4. 기상청 `getVilageFcst`를 호출한다.
5. 응답의 `resultCode=00`을 확인한다.
6. 응답에 포함된 서비스 대상 미래 시간대들을 파싱한다.
7. `PTY`와 `SKY`를 MULO 내부 날씨 상태로 변환한다.
8. `cache_date`를 요청일의 KST 날짜로 지정하고 격자별·예보시각별 행을 MySQL에 일괄 저장한다.
9. `target_forecast_at`에 해당하는 캐시를 반환한다.

### 6.2 같은 날의 후속 요청

같은 KST 날짜에 동일 격자의 요청이 들어오면 저장된 시간대별 캐시를 조회한다.

- 요청한 `target_forecast_at` 캐시가 있으면 그대로 반환한다.
- 더 최신 `base_at`이 공개됐는지는 검사하지 않는다.
- 같은 격자라는 이유만으로 하나의 날씨 값을 하루 종일 반환하지 않고, 요청 시각에 대응하는 `forecast_at` 행을 선택한다.
- 캐시 응답에는 실제 사용한 `forecastAt`을 포함한다.
- 해당 날짜와 격자의 성공 캐시는 있지만 요청한 `target_forecast_at` 행이 없으면 외부 API를 다시 호출하지 않고 날씨 확보 실패로 처리한다.

즉, **발표본은 당일 최초 호출 결과로 고정하지만 시간대별 날씨 값은 요청 시각에 맞게 달라진다.**

### 6.3 날짜 변경

KST 날짜가 바뀌면 전날 `cache_date`의 캐시를 당일 최초 외부 호출 여부 판단에 사용하지 않는다. 새 날짜의 최초 요청은 기상청 API를 호출하여 새 `cache_date`의 예보 묶음을 저장한다.

과거 캐시 삭제와 보관 기간은 별도 운영 정책으로 정한다. V1 구현에서는 당일 캐시 조회가 정확히 분리되는 것을 우선한다.

## 7. MySQL 저장 모델

최신 테이블 정의서의 `weather_grids`, `weather_grid_forecasts` 구조를 기본으로 사용한다.

### 7.1 `weather_grids`

격자 좌표를 중복 없이 관리한다.

```text
weather_grid_id
grid_x
grid_y
created_at
```

고유 조건:

```text
UNIQUE (grid_x, grid_y)
```

### 7.2 `weather_grid_forecasts`

한 격자의 시간대별 예보 캐시를 저장한다.

```text
weather_grid_forecast_id
weather_grid_id
cache_date
forecast_at
temperature
weather_condition
base_at
fetched_at
```

고유 조건:

```text
UNIQUE (weather_grid_id, cache_date, forecast_at)
```

`cache_date`는 해당 격자의 일 단위 캐시를 구분하는 KST 날짜다. 같은 `forecast_at`이 전날 캐시와 오늘 캐시에 모두 포함될 수 있으므로 `cache_date`를 고유 조건에 포함한다.

같은 `cache_date`에서는 더 최신 발표본으로 기존 행을 갱신하지 않는다. KST 날짜가 바뀌면 새로운 `cache_date`로 행을 저장하므로 전날 캐시와 예보시각이 겹쳐도 충돌하지 않는다.

현재 저장소의 `V2__create_weather.sql`은 `city_name`당 한 행만 허용하므로 이 설계와 일치하지 않는다. 구현 단계에서는 적용된 기존 migration을 수정하지 않고 새로운 Flyway migration으로 스키마를 변경해야 한다. DB 스키마 변경은 `AGENTS.md`에 따라 구현 전 별도 승인을 받는다.

## 8. 날씨 상태 변환

MULO 내부 상태는 다음 7개만 사용한다.

```text
CLEAR
CLOUDY
OVERCAST
RAIN
SNOW
RAIN_SNOW
SHOWER
```

강수 상태인 `PTY`를 하늘 상태인 `SKY`보다 우선한다.

```text
PTY가 강수 상태임 -> PTY를 기준으로 변환
PTY가 강수 없음임 -> SKY를 CLEAR/CLOUDY/OVERCAST로 변환
```

원시 `PTY`, `SKY` 값은 변환에만 사용하고 DB에는 저장하지 않는다.

## 9. API 계약 방향

날씨 조회 API는 다음 형식을 유지한다.

```http
GET /api/weather?latitude={latitude}&longitude={longitude}&at={dateTime}
```

성공 응답은 실제 선택된 예보시각을 명시한다.

```json
{
  "message": "날씨 조회 성공",
  "data": {
    "forecastAt": "2026-09-20T11:00:00+09:00",
    "temperature": 26.0,
    "weatherCondition": "CLEAR"
  }
}
```

`forecastAt`을 반환하면 11시 10분 요청에서 11시 예보를 사용했는지, 11시 40분 요청에서 12시 예보를 사용했는지 클라이언트가 확인할 수 있다.

## 10. 장애 처리

### 자물쇠 생성

허용된 발표 회차에서 날씨를 확보하지 못해도 자물쇠 생성은 계속한다. `records.weather_condition`, `records.temperature`는 `NULL`로 저장한다.

### 추천 생성

추천 생성에는 날씨와 기온이 필수다. 허용된 회차 조회와 캐시 조회가 모두 실패하면 `502 WEATHER_API_ERROR`로 추천을 생성하지 않는다.

### 날씨 조회 API

캐시와 외부 API에서 모두 날씨를 확보하지 못하면 공통 오류 형식으로 `WEATHER_API_ERROR`를 반환한다. 세부 HTTP 상태와 입력 좌표 범위 오류는 OpenAPI 계약과 구현 계획에서 최종 확인한다.

완료된 이전 시간대 요청은 `400 INVALID_WEATHER_REQUEST_TIME`을 반환한다. 위도·경도·`at`의
누락, 형식 오류, 전 지구 범위 초과는 `400 INVALID_INPUT_VALUE`를 반환한다.

## 11. 동시 요청

동일 격자의 최초 요청이 동시에 들어오면 외부 API가 중복 호출될 가능성이 있다. V1에서는 DB의 고유 제약조건으로 중복 행 저장을 방지하고, 저장 경합이 발생하면 기존 캐시를 다시 조회한다.

애플리케이션 단위 락이나 분산 락은 V1 범위에 도입하지 않는다. 중복 외부 호출이 실제 운영 문제로 확인되면 후속 버전에서 보완한다.

## 12. 구현 범위와 비범위

### 구현 범위

- 좌표의 기상청 격자 변환
- 요청 시각의 가장 가까운 정각 계산
- 목표 예보시각을 포함하는 발표 회차 선택
- 기상청 클라이언트 호출과 응답 검증
- 시간대별 데이터 그룹화
- MULO 날씨 상태 변환
- MySQL 일괄 저장과 당일 캐시 조회
- `GET /api/weather`
- 자물쇠·추천 도메인이 재사용할 날씨 조회 Service 경계

### 구현하지 않는 범위

- Redis
- 실시간 관측 API `getUltraSrtNcst`
- 스케줄러를 이용한 선제 갱신
- 같은 날 최신 발표본으로 캐시 갱신
- 풍속·습도·강수확률 저장 또는 응답
- 분산 락
- 장기 날씨 이력 분석

## 13. 검증 기준

- `11:10` 요청이 `11:00` 예보를 선택한다.
- `11:40` 요청이 `12:00` 예보를 선택한다.
- 최신 발표본에 목표 예보시각이 없으면 이를 포함하는 이전 회차를 선택한다.
- 최초 호출 응답의 여러 시간대를 한 번에 저장한다.
- 같은 날 같은 격자의 후속 요청은 목표 예보시각 행이 없어도 외부 API를 다시 호출하지 않는다.
- 전날과 오늘의 응답에 동일한 미래 `forecast_at`이 포함되어도 `cache_date`로 구분되어 저장된다.
- 같은 격자라도 요청 시간대에 따라 서로 다른 `forecast_at` 행을 반환한다.
- KST 날짜가 변경되면 전날 캐시만으로 외부 호출을 생략하지 않는다.
- `PTY`가 `SKY`보다 우선하여 최종 날씨 상태가 결정된다.
- 기상청 키와 원시 응답은 로그나 API 응답에 노출하지 않는다.

## 14. 근거

- 실제 `getVilageFcst` 호출에서 한 번의 응답에 여러 `fcstDate`, `fcstTime`, `category` 항목이 반환되는 것을 확인했다.
- `baseTime=1100` 응답은 첫 예보시각이 `1200`이었으므로 `baseTime`과 요청 시각 또는 현재 날씨 시각을 동일하게 취급할 수 없다.
- HTTP 200 응답에서도 `03 NO_DATA`와 일시적인 `01 APPLICATION_ERROR`가 관찰됐으므로 `resultCode` 검증과 제한적인 이전 회차 처리가 필요하다.
- 최신 정책 문서의 격자별·예보시각별 저장 구조와 날씨 상태 변환 규칙은 유지한다.
