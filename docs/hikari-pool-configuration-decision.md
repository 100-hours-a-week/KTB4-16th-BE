# HikariCP 풀 크기와 커넥션 획득 대기시간 초기 설정

## 결정

`spring.datasource.hikari.maximum-pool-size`는 **3**, `connection-timeout`은 **5,000ms**로 명시한다. 대기열이나 API 전체 타임아웃을 새로 도입하지 않는다. 두 값은 운영 환경에서 재검증할 초기 설정이며 최적값으로 확정하지 않는다.

## 기존 상태와 변경

기존 `application.yaml`에는 HikariCP 값이 명시되지 않았다. HikariCP 문서 기준 기본값은 최대 커넥션 10개, 커넥션 획득 대기 30,000ms다. 이번 변경에서는 기존 `spring.datasource` 아래에 다음만 추가한다.

```yaml
hikari:
  maximum-pool-size: 3
  connection-timeout: 5000
```

`maximum-pool-size`는 유휴 상태와 사용 중인 커넥션을 포함한 풀의 최대 크기다. 풀이 모두 사용 중이면 커넥션 획득 요청은 최대 `connection-timeout` 동안 기다린다. 5초 안에 커넥션을 얻지 못한 **해당 요청**에서 예외가 발생한다. 이 값은 SQL 실행시간, 전체 API 응답시간 또는 사용자 대기열의 최대 시간을 제한하지 않는다.

## 선정 근거

아래 수치는 프로젝트에서 수행한 부하 테스트 결과를 사용자로부터 전달받은 것이다. 테스트 스크립트와 원본 측정 결과는 이 문서에서 검증하지 않았다.

| 지표 | 풀 10개 | 풀 3개 |
|---|---:|---:|
| 전체 처리량 | 64.4 RPS | 약 63 RPS |
| 전체 API 응답시간 p95 | 5.5초 | 5.04초 |

풀을 3개로 줄여도 측정된 처리량 차이가 작으므로 3개를 초기값으로 사용한다. 그러나 이 비교만으로 HikariCP가 병목이 아니라고 확정할 수 없다. 같은 테스트에서 100 VU의 전체 p95는 4.534초, 200 VU의 전체 p95는 10.395초였고, 200 VU의 처리량은 약 63 RPS에서 정체했다. 부하 증가에 따른 응답시간 상승의 원인은 별도로 확인해야 한다.

HikariCP 공식 문서는 `connectionTimeout`의 기본값을 30초로 설명하며, 프로젝트에 보편적으로 적합한 5초를 권장하지 않는다. 5초는 커넥션이 부족할 때 요청이 기본값인 30초 동안 연결 획득을 기다리지 않도록 하는 초기 실험값이다. 3초보다 연결 반환을 기다릴 여유를 주면서 30초보다 일찍 실패를 감지한다. 풀 크기 3개와 타임아웃 5초 사이에 공식적인 비례 공식이 있는 것은 아니다.

## 검증 방법과 판단 기준

동일한 부하 시나리오에서 `connection-timeout`만 30초, 5초, 3초로 바꾸어 비교한다. 풀 크기, 요청 구성, VU, 부하 지속시간, 테스트 환경을 동일하게 유지하고 충분히 지속되는 부하 구간도 포함한다.

- 커넥션 획득 대기시간과 실제 점유시간
- Active / Idle / Pending 커넥션 수
- 커넥션 획득 타임아웃 건수
- 전체 API 응답시간 p95, p99
- **성공 요청 기준** 처리량(RPS)과 실패율

전체 API p95는 커넥션 획득 대기시간과 다르다. 타임아웃을 줄여 빠르게 실패한 요청이 늘었다면, 전체 응답시간이 낮아져도 성능 개선으로 판정하지 않는다. 성공 처리량과 실패율을 함께 비교한다. 설정 변경만으로 기존 병목이 해결되었다고 판단하지 않는다.
